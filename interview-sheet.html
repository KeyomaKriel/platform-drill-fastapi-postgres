Interview Sheet

One page. Fallback loop, spoken frame, core commands, symptom map. Nothing else.

Spoken frame

"I'm going to check the workload first, then the traffic path, then dependencies. So first I'll look at pods and see whether this is a startup or readiness problem. If the pods are healthy, I'll move to service and endpoints. If that looks fine, I'll check ingress or the external path."

If they ask you to close your reference material

"I've closed it. I'll work directly from the cluster state and talk through my reasoning."

Fallback loop

  1. kubectl get pods -n <ns> — check pod state first. Are they Running + Ready?
  2. If a pod looks bad: kubectl describe pod <pod> -n <ns> and kubectl logs <pod> -n <ns> --previous
  3. If pods look healthy: kubectl get svc -n <ns> and kubectl get endpoints <svc> -n <ns>
  4. If service looks fine but external path fails: kubectl get ingress -n <ns> and kubectl describe ingress <ing>
  5. If app is up but feature fails: check logs, env, and dependency reachability

Core commands

kubectl get pods -n <ns>
kubectl describe pod <pod> -n <ns>
kubectl logs <pod> -n <ns> --previous
kubectl get svc -n <ns>
kubectl get endpoints <svc> -n <ns>
kubectl get ingress -n <ns>

Symptom map

▶CrashLoopBackOff or restarts climbing
kubectl logs and kubectl describe pod. Logs route you to the actual cause: config, dependency, DNS, OOM, or code.
▶Running but not Ready (0/1)
kubectl describe pod — check readiness probe spec and Events. Probe path/port mismatch is the most common cause.
▶Service failing / 502 / 503
kubectl get endpoints and kubectl describe svc. Empty endpoints = selector mismatch or pods not Ready.
▶External route failing (internal works)
kubectl get ingress and kubectl describe ingress. Check ingressClassName, backend service name, backend port.
▶Feature failing but app is up
Check logs for dependency errors. Then kubectl exec -- env and compare config values against actual service names and credentials.
