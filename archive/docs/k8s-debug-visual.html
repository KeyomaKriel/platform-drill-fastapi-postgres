Kubernetes Troubleshooting Interview Cheat Sheet

Use the flow first. Use the views underneath only as support. This is for reasoning fast under pressure, not memorising the whole theory tree.

1

Start

Did the Pod get created? Did the container start? Think image, command, env, mounts, resources.

2

Stay up

Does it keep running? Is it Ready? Think crashes, OOM, liveness, readiness, startup, bad config.

3

Receive traffic

Can the Service reach the Pod? Think selectors, endpoints, ports, targetPort, Ingress routing.

4

Reach Dep

Can the app reach DB, DNS, APIs, cluster services, secrets-backed resources, permissions?

Memory hook

Start → Stay up → Receive traffic → Reach Dep

What interviewers feel
  • You orient quickly.
  • You follow evidence, not guesses.
  • You know the next 1–3 checks.
  • You explain why you are checking something.

Support views: use these only to locate the problem

Supports Start

Management view

Deployment ↓ ReplicaSet ↓ Pods

Use when asking: are the right Pods being created, updated, and kept alive?

Supports Stay up & Traffic

Health view

kubelet / probes ↓ Pod / container

Readiness = should traffic be sent? Liveness = should it restart? Startup = has boot finished?

Supports Traffic & Dep

Traffic view

Client ↓ Ingress ↓ Service ↓ Pod ↓ app

Use when asking: does internal routing work, and does external routing work?

Supports Start & Stay up & Dep

Dependencies view

Config / Secret / DNS / DB / API ↓ Pod / app

Use when asking: did the app get what it needs, and can it reach what it needs?

Fast symptom map

Won’t start

Think Start

ImagePullBackOff, ErrImagePull, bad command, missing env, bad mounts, bad image tag.

Starts but not serving

Think Stay up

CrashLoopBackOff, 0/1 Ready, readiness failure, liveness restart, app not listening, OOMKilled.

Works internally, fails externally

Think Receive traffic

Ingress host/path, backend Service, TLS, controller issue, service port/targetPort mismatch.

Starts and routes, still broken

Think Reach Dep

DB auth, DNS, RBAC, IAM, NetworkPolicy, external API creds, storage, upstream service failures.

5 commands that matter most

kubectl get pods kubectl describe pod <pod> kubectl logs <pod> --previous kubectl get svc kubectl get endpoints

These cover state, events, app output, Service definition, and real Service backends.

Core concepts to actually know

PodWhere the app runs.
DeploymentManager of Pods.
ServiceStable path to Pods.
IngressExternal HTTP(S) router.
Labels/selectorsMatching glue.
EndpointsReal Service backends.
ProbesHealth and readiness judgment.
ConfigMap/SecretInputs to the app.

What to say in the interview

Senior-sounding narration “I’m starting with the symptom, putting it into the likely failure bucket, and checking the fastest evidence first: pod state, describe output, logs, service backends, then ingress if needed.”
Deployment manages Pods. Probes judge Pods. Services send to Pods. Ingress sends to Services. Config and Secrets feed Pods.
Do not memorise isolated terms first. Attach each concept to a job, a failure shape, and a first check.
