Kubernetes Troubleshooting Interview Sheet

Use the four-part frame first. Then run the same execution loop every time.
Kubernetes' own debugging docs start with triage by object or layer, and the pod lifecycle docs explicitly treat CrashLoopBackOff as an observed condition rather than the underlying cause.
Symptom first, root cause second.
Core Frame
1

Start

Was the Pod created, scheduled, and able to start its container?
  • Pending
  • ErrImagePull / ImagePullBackOff
  • CreateContainerConfigError / CreateContainerError
  • Init container failure
  • Command / entrypoint / args problem
  • Missing ConfigMap / Secret / volume mount
  • PVC not binding
  • Node capacity / taints / affinity / scheduling blockers
2

Stay Up

Did the app keep running and become Ready?
  • CrashLoopBackOff
  • Error
  • Running but 0/1 Ready
  • Restarts climbing
  • Probe failures
  • OOMKilled / exit 137
  • App boot failure
  • Startup dependency failure
3

Receive Traffic

Can traffic reach the app through the Kubernetes routing path?
  • Service has no working backends
  • Selector mismatch
  • Pods not Ready, so no usable endpoints
  • Wrong port / targetPort
  • Wrong named port
  • Ingress host / path / backend mismatch
  • External path broken while internal Service path works
4

Reach Dep

Can the app reach what it depends on?
  • DB / cache / API connection failure
  • DNS resolution failure
  • Wrong hostname / namespace
  • Missing or wrong Secret / env var
  • Auth / permission failure
  • Service account / RBAC issue
  • Egress blocked by NetworkPolicy
  • Storage dependency problem
Execution Loop
1 Classify Start, Stay Up, Receive Traffic, or Reach Dep? →
2 Inspect Nearest truth source. Pods broken? State, describe, logs. Pods healthy? Route outward. →
3 Route By evidence, not guess. Symptom shows where to look, not the root cause. →
4 Fix Smallest justified change. One thing for one reason. →
5 Verify End to end. Do not stop at "Pod is Running".
Fast Symptom Map
Start Pod missing, Pending, or never becomes Running
  • Scheduling / resource pressure
  • PVC / storage binding
  • Taints / affinity / node placement
  • Image pull failure
  • Container creation failure
  • Bad config / secret / volume reference
Start ErrImagePull / ImagePullBackOff
  • Wrong image name or tag
  • Registry auth problem
  • Image not accessible
  • Pull policy / registry reachability issue
Start CreateContainerConfigError / CreateContainerError
  • Missing Secret / ConfigMap
  • Bad env reference
  • Bad volume or mount
  • Bad command / args / container startup definition
Start Init container failure
  • Dependency setup failure before app container starts
  • Bad image / command / mount / config in init container
Stay Up CrashLoopBackOff
This is a symptom, not the root cause. Likely root-cause branches after logs:
  • Bad config / env / secret
  • Startup dependency failure
  • Bad hostname / DNS / namespace
  • App boot failure
  • Probe-driven restart
  • OOMKilled
  • Bad command / entrypoint
Stay Up Running but 0/1 Ready
  • Readiness probe failure
  • App boot incomplete
  • Dependency reachable enough to start, but not enough to serve
  • Container alive but not ready for traffic
Stay Up Running, Ready, but restarts increasing
  • Liveness probe failure
  • Intermittent startup/runtime crash
  • Memory pressure / OOM
  • App error after boot
Stay Up OOMKilled / exit 137
  • Memory limit too low
  • Boot spike or runtime memory growth
  • Container killed and restarted by kubelet
Traffic Pod healthy, but Service path fails
  • Selector mismatch
  • Pods not Ready, so endpoints absent or not usable
  • Wrong service port / targetPort
  • Wrong named port
  • Service exists but points nowhere useful
Traffic Endpoints / EndpointSlices empty or wrong
  • Service selector does not match Pod labels
  • Matching Pods are not Ready
  • Backend set is not what you think it is
Traffic Service works internally, external route fails
  • Ingress rule issue
  • Wrong host / path
  • Wrong backend service or port
  • Ingress controller issue
Reach Dep App responds, but feature fails when calling DB / API / storage
  • Wrong env / secret value
  • DNS or service discovery failure
  • Connection refused / auth failure
  • RBAC / service account issue
  • NetworkPolicy or egress restriction
  • Storage problem
Reach Dep Forbidden / Unauthorized
  • Missing RBAC permission
  • Wrong service account
  • Wrong identity assumptions
Reach Dep "Name or service not known", lookup failures, wrong hostname behaviour
  • Bad service DNS name
  • Wrong namespace assumption
  • Typo in hostname
  • DNS issue, not application routing
Reach Dep Traffic silently blocked despite objects looking correct also Traffic
  • NetworkPolicy blocking pod-to-pod or egress traffic
  • Policy allows some paths but not the one you need
Meta Rollout stuck or deployment not progressing
Not a root cause by itself — inspect the new Pods.
Route to: Start if new Pods cannot start. Stay Up if new Pods crash or fail probes. Receive Traffic if Pods are healthy but not serving. Reach Dep if the app is up but broken against dependencies.
Meta Job / CronJob issue
Same root-cause buckets as Pods.
Route to: Start if Job Pod cannot start. Stay Up if Job Pod crashes. Reach Dep if job logic fails against dependencies.
Support Views

Management View

Deployment → ReplicaSet → Pods
Use when asking:
  • Are the right Pods being created?
  • Is the rollout progressing?
  • Is the expected replica set actually healthy?

Health View

kubelet / probes → Pod / container
Use when asking:
  • Did the app start?
  • Did it stay alive?
  • Is it Ready to receive traffic?
  • Is kubelet restarting it?

Traffic View

Client → Ingress → Service → EndpointSlices → Pod → app
Use when asking:
  • Internal service-routing or external-routing issue?
  • Is the Service actually pointing to healthy backends?

Dependencies View

Config / Secret / DNS / DB / API / storage / identity → Pod / app
Use when asking:
  • Did the app get the inputs it needs?
  • Can it reach the systems it depends on?
  • Does it have the permissions it needs?

What to Say in the Interview

"I'm going to start with the symptom, not jump to a root cause."
"First I want the nearest truth source."
"If the Pod is broken, I'll inspect Pod state, describe output, and logs."
"If the Pod is healthy, I'll move outward from Pod to Service to Ingress."
"I want to make one justified change, then verify end to end."

This matches the official debugging flow and shows controlled reasoning rather than guesswork.

Verification Order

After any fix, verify in this order:

  1. Pod state is healthy
  2. Readiness is healthy
  3. Endpoints / EndpointSlices are populated correctly
  4. Service path works
  5. Ingress / external path works, if relevant
  6. The actual app behaviour works end to end
Do not stop at "Pods are Running". Services depend on backend endpoints, and ingress only proves the external edge if the backend chain is sound.
Frame: Start → Stay Up → Receive Traffic → Reach Dep   |   Rule: Symptom first, root cause second
Loop: Classify → Inspect nearest layer → Route by evidence → Smallest fix → Verify end to end
