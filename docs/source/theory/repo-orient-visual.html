Shape

Goal: get the repo map.

Check

  • Where app code lives
  • Where Docker/build files live
  • Where K8s manifests or Helm chart live
  • Whether it is one app or multiple services

Commands

pwd

Narration

“I’m getting the repo shape first: where the application code is, where the container/build config is, and where the Kubernetes deployment config lives.”
2

Start

Goal: understand how the app actually runs.

Check

  • Entrypoint or main file
  • Dockerfile
  • command / args
  • Listening port
  • Health endpoints
  • Whether startup depends on DB or another service

Look at

  • Dockerfile
  • Main app file
  • package.json / requirements.txt / pyproject.toml
  • Deployment command / args

Narration

“Now I’m finding the startup path: what process runs in the container, what port it listens on, and whether startup depends on config or external services.”
3

Supply

Goal: understand what the app needs.

Check

  • Env vars
  • ConfigMaps / Secrets
  • DB URL / host / creds
  • Upstream service names / URLs
  • Mounted files
  • Anything mandatory for startup

Look at

  • App config reads in code
  • Deployment env section
  • ConfigMap / Secret manifests

Narration

“Next I’m checking the input surface: env vars, config, secrets, and any dependencies the app needs to talk to.”
4

Ship

Goal: understand how Kubernetes runs and exposes it.

Check

  • Deployment
  • Labels on Pod template
  • Service selector
  • Service port and targetPort
  • Probes
  • Ingress host/path/backend

Look at

  • k8s/
  • manifests/
  • helm/templates/

Narration

“Now I’m tracing how Kubernetes is expected to run and expose the app: Deployment, probes, Service wiring, and any Ingress routing.”
5

Signals

Goal: know where truth will show up when it breaks.

Check

  • Health endpoints
  • Log output location
  • What describe pod would likely show
  • How to prove Pod vs Service vs Ingress quickly

Narration

“Finally, I want the quickest signals: where startup failures, readiness problems, service wiring issues, or ingress issues would show up first.”

What this buys you

  • You stop guessing
  • You know where evidence should appear first
  • You can separate startup, readiness, wiring, and exposure fast

The 5 questions to answer before touching fixes

  1. What is this app and stack?
  2. What starts it?
  3. What does it need to work?
  4. How is it exposed in Kubernetes?
  5. Where would failure show up first?

Fast repo-orientation flow

pwd
ls
tree -L 2
find . -maxdepth 2 -type f | sort
cat README.md
cat Dockerfile
find k8s -maxdepth 2 -type f | sort

Then inspect:
- app entry file
- Deployment
- Service
- Ingress
- ConfigMap / Secret

What you are trying to extract

  • App: language, main file, port, health endpoints
  • Container: how it starts
  • Inputs: env vars, secrets, dependencies
  • K8s: Deployment, probes, Service, Ingress
  • Likely breakpoints: startup, readiness, service wiring, ingress routing, dependency config

What not to do

  • Do not read the whole codebase
  • Do not explain business logic in depth
  • Do not open every file
  • Do not start fixing before you know startup path and K8s wiring

Memorize this

  • What is it?
  • How does it start?
  • What does it need?
  • How is it deployed?
  • Where will it fail first?

Ultra-short narration script

“I’m mapping the repo first.”
“Now I’m checking how the app starts and what port and health endpoints it uses.”
“Next I’m checking config, secrets, and dependencies.”
“Now I’m looking at Deployment, probes, Service, and Ingress.”
“At this point I should know the quickest likely failure points and where the evidence will show up.”
Use this as a first-pass interview orientation sheet, not as a substitute for actual evidence from kubectl, logs, describe output, and the repo itself.
