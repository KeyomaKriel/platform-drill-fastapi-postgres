Kubernetes Troubleshooting Interview Sheet

Use the four-stage flow first. Use the support views only to place the problem more precisely.

1

Start

Was the Pod created, and did the container actually start? Think image pull, command, env, mounts, admission, scheduling.

2

Stay up

Does it keep running and become Ready? Think crashes, probes, startup timing, OOM, bad config, app boot failures.

3

Receive Traffic

Can traffic reach the Pod through the Service path? Think selectors, EndpointSlices, ports, targetPort, path routing.

4

Reach Dep

Can the app reach its dependencies? Think DB, DNS, external APIs, storage, secrets, RBAC, network rules, identity.

Fast symptom map

Pod missing or never becomes Running

Think Start

Put it in the creation/start bucket first.

  • Pending: scheduling, node pressure, PVC, affinity, taints.
  • ErrImagePull / ImagePullBackOff: image name, tag, auth, registry reachability.
  • CreateContainerConfigError / CreateContainerError: env, secret, config, mount, command.

Pod runs briefly or shows 0/1 Ready

Think Stay up

Assume boot or health gating until proven otherwise.

  • CrashLoopBackOff: app exits, bad startup dependency, bad flags, bad config.
  • OOMKilled / exit 137: resource limits too low or leak / spike during boot.
  • Readiness failing: app alive but not actually ready to serve.

App is healthy inside Pod, but traffic still fails

Think Receive Traffic

Split internal routing from external routing.

  • No endpoints or wrong EndpointSlices: selector mismatch or not Ready.
  • Service port / targetPort mismatch: Service exists but points to wrong container port.
  • Ingress host/path/backend issue: external path broken while internal Service works.

Requests reach app, but feature still fails

Think Reach Dep

Now think downstream systems, not Kubernetes routing.

  • DB connection/auth failures, DNS resolution failures, bad upstream URL.
  • Missing secret values, expired creds, bad IAM/RBAC identity.
  • NetworkPolicy, egress limits, storage, external API failures.

Support views

Supports Start

Management view

Deployment ↓ ReplicaSet ↓ Pods

Use when asking whether the right Pods are being created, replaced, and kept at the expected count.

Supports Stay up

Health view

kubelet / probes ↓ Pod / container

Use when asking whether the app booted, stayed alive, and became eligible to receive traffic.

Supports Receive Traffic

Traffic view

Client ↓ Ingress ↓ Service ↓ Pod ↓ app

Use when asking whether the request path is broken externally, at the Service layer, or inside the Pod.

Supports Start / Stay up / Reach Dep

Dependencies view

Config / Secret / DNS / DB / API ↓ Pod / app

Use when asking whether the app got the inputs it needs and can reach the systems it depends on.

How to learn it

Do not memorise isolated terms first. Attach each concept to a job, a failure shape, and a first check.
