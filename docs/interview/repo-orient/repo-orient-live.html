Repo Orientation

Answer five things fast. Read five files. Say what you found.

1What kind of app?
2What process starts it?
3What port?
4What endpoints?
5Which manifests wire it?
10 seconds — Spot the framework
pwd && ls && tree -L 2

Django

manage.py + config/ + models.py + views.py + urls.py + migrations/
"This looks like a Django app. manage.py is the signal. Settings in the project package, routes in urls.py, handlers in views.py."

Simple Python

app.py or main.py + requirements.txt
"This looks like a simpler Python service. Routes and startup logic should be concentrated in one or two files."

Go

go.mod + main.go
"This is a Go service. I'm going to check main.go for startup, routes, and the listening port."
3–4 minutes — Read these 5 files only

1. Dockerfile

  • Port EXPOSE — the container port. Service targetPort and probe port must match this.
  • Start CMD / ENTRYPOINT — what process runs. If it references a WSGI module path, note which package.
  • Build Base image, single-stage vs multi-stage.
"The Dockerfile tells me this is a [language] app running [process] on port [N]. This port is the contract that probes and Service targetPort must match."

2. App code — routes, health, config

Django: config/settings.py (DB config) + */urls.py (routes) + */views.py (handlers)
Python: app.py or main.py
Go: main.go

  • Probe Health/readiness endpoints — what path, what they check. This is what the probe must target.
  • Routes All endpoints and what they do.
  • Config Which env var names for DB? (PG*, POSTGRES_*, DB_* — varies by app)
  • Start Startup behaviour — seeds data? Runs migrations? Crashes if DB down?
"The app has [N] endpoints. Health check is [path] and it [checks DB / always 200]. DB config comes from env vars [list]. On startup it [seeds/migrates/crashes if DB down]."

3. Deployment manifest

  • Image Image name/tag, imagePullPolicy.
  • Labels Pod template labels — the Service selector must match these.
  • Config envFrom — which ConfigMaps and Secrets. These names must exist in the namespace.
  • Probes Path, port, timing. Must match what the app actually serves.
  • Init How many init containers? What does each do? Which read from ConfigMap/Secret?
  • Override command/args — if present, overrides Dockerfile CMD.
"The Deployment runs [image] with [N] init containers. Config comes from [names]. Probes target [path:port]. Migrations/seeding happen [where]."

4. Service manifest

  • Selector Must match Deployment pod labels exactly.
  • Ports port (what Ingress connects to) → targetPort (must match container port).
"Service selects [labels], maps port [X] to targetPort [Y]. If either drifts from the Deployment, traffic fails silently while pods look healthy."

5. Ingress manifest

  • Backend Service name and port — must match the Service.
  • Routing IngressClassName, host, path rules.
"Ingress routes [path] to [service] on port [N]. This is the last hop before the user-visible URL."

Also check: ConfigMap + Secret + DB manifests

  • Values DB host, port, database name, creds. Cross-reference: does DB host match the DB Service name?
  • Creds Do app creds match DB creds? Any mismatch is the most common failure domain.
  • DB Service Service name = the hostname the app config must point to.
"Config points to DB host [name] — I'm verifying that matches the actual DB Service name and that creds match on both sides."
Verify — The contract chain

Every connection in this chain is a contract between two manifests. If any link breaks, the app fails.

Config chain

App reads DB host from env var [PGHOST / POSTGRES_HOST / DB_HOST]
  → Deployment envFrom references ConfigMap [name]
    → ConfigMap value = DB Service name
      → DB Service selector = DB pod labels
        → DB pod Running + Ready

Traffic chain

App listens on port [N]
  → Deployment containerPort = [N]
    → Service targetPort = [N], port = [M]
      → Ingress backend port = [M]
        → curl localhost/ works
kubectl get pods -n [ns]                # Running + Ready?
kubectl get endpoints -n [ns]           # Populated?
curl localhost/[health-path]            # 200?
curl localhost/[data-path]              # Returns data?
"Files told me what should happen. These commands tell me what is actually happening. Any gap is where the problem lives — and I want to verify the full user-visible path, not just that pods are Running."
Narration script

Say these out loud during orientation. Keep it plain.

  1. "I'm mapping the repo first — where the app code, container config, and Kubernetes manifests live."
  2. "This looks like a [Django / Python / Go] app because of [manage.py / app.py / go.mod]."
  3. "I'm checking the Dockerfile to confirm the startup command and app port."
  4. "Now I'm checking the app routes and health endpoints so I know what the probes and traffic path should target."
  5. "Now I'm checking the Deployment, Service, and Ingress to verify the startup, config, and traffic contracts."
  6. "I'm cross-referencing the config values against the Service names and DB config — any mismatch here is the most common failure."
  7. "Now I'm verifying live — pods healthy, endpoints populated, and the user-visible path returns expected responses."
Don't go deeper than this
  • Django models in detail
  • Serializers / middleware
  • Business logic
  • Every endpoint's response shape
  • Deep framework conventions
  • Every manifest field
  • Test files
  • CI/CD config

You are not being tested on framework expertise. You are being tested on whether you can orient to an unfamiliar repo, understand how it's deployed, and verify the contracts that make it work.
