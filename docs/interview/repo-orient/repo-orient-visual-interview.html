Repo Orientation

Recognize the app. Read 5 files. Say what you found. Verify live. Move on.

You are not being tested on framework expertise. You are being tested on whether you can orient to an unfamiliar repo, understand how it's deployed, and verify the contracts that make it work.

3–4 minutes — Read these files in order

Open one, extract everything, move on

1

Dockerfile

  • Port EXPOSE — the container port. Probes and Service targetPort must match this.
  • Start CMD / ENTRYPOINT — what process runs. Note WSGI module paths.
  • Build Single-stage vs multi-stage. Base image confirms language.
The port here is the source-of-truth contract. If the Deployment, Service, or probes reference a different port, that's likely the break.
"I'm checking what actually starts in the container and which port it listens on, because that has to match probes and Service targetPort."
2

App code — routes, health, DB config

Django: config/settings.py → */urls.py → */views.py  |  Python: app.py  |  Go: main.go

  • Probe Health/readiness path — what path returns 200, what it checks. This is what the probe must target.
  • Routes All user-visible endpoints and what they do.
  • Config Which env var names for DB? (PG*, POSTGRES_*, DB_* — varies)
  • Startup Does it seed data? Run migrations? Crash if DB unreachable?
Probe path mismatches are one of the most common failures. If the app serves /api/v1/status but the probe targets /health, readiness silently fails.
"I'm checking which paths the app really serves and whether health endpoints exist, because probe-path mismatches are a common failure."
3

Deployment manifest

  • Image Image name/tag, imagePullPolicy.
  • Override command / args — if present, overrides Dockerfile CMD.
  • Config envFrom — which ConfigMaps and Secrets. These names must exist in the namespace.
  • Probes Path, port, timing. Must match what the app actually serves on the container port.
  • Labels Pod template labels — the Service selector must match these exactly.
  • Init How many init containers? What does each do? Which read from ConfigMap/Secret?
This is where most contracts live: image, config references, probe targets, labels. Any naming mismatch here silently breaks things.
"Now I'm checking how Kubernetes runs the app: image, startup override, config injection, probes, and init containers."
4

Service manifest

  • Selector Must match Deployment pod labels. Any character difference = empty endpoints.
  • Ports port (what Ingress connects to) → targetPort (must match container port).
If the selector doesn't match pod labels, endpoints are empty and traffic silently fails while pods look healthy.
"This tells me how traffic reaches the pod. The selector must match pod labels, and targetPort must match the app's listening port."
5

Ingress manifest

  • Backend Service name and port — must match the Service exactly.
  • Routing ingressClassName, host, path rules.
This is the last hop before the user-visible URL. If the backend name or port is wrong, external access fails while internal routing still works.
"This is the user-visible entry path. If the app is unreachable externally, this is one of the first contracts I'd verify."
6

ConfigMap + Secret — check when needed

  • Values DB host must match the DB Service name. DB name, user, password must match on both sides.
  • Names ConfigMap/Secret names must match what the Deployment envFrom references.
Config mismatches between the app side and the database side are the single most common failure domain. Any naming drift breaks the connection.
"I'm checking whether the config names and values actually match what the app and dependent service expect."
After orientation — First live checks

Verify reality matches what you read

kubectl get pods -n <ns>                # Running + Ready?
kubectl get endpoints -n <ns>           # Populated for each Service?
kubectl get ingress -n <ns>             # ADDRESS populated?
curl localhost/<health-path>            # 200?
curl localhost/<data-path>              # Returns data?
"Files told me what should happen. These commands tell me what is actually happening. Any gap between the two is where the problem lives — and I want to verify the full user-visible path, not just that pods are Running."
