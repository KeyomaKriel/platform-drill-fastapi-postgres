Interview Quick Reference

Repo Orientation

Recognize the app. Read 5 files. Say what you found. Verify live. Move on.

You are not being tested on framework expertise. You are being tested on whether you can orient to an unfamiliar repo, understand how it's deployed, and verify the contracts that make it work.

3–4 minutes — Read these files in order

Open one, extract everything, move on

1

Dockerfile

"I'm opening the Dockerfile first to see what actually starts in the container and what port it binds to."

Find: CMD / ENTRYPOINT

This is the startup command. Look for the process name and the bind port (e.g. --bind 0.0.0.0:8200). If it references a WSGI module like config.wsgi:application, note which project package that points to.

"The startup command is [process] binding to port [N]. That port is what probes and the Service targetPort must match."

Find: EXPOSE

EXPOSE is a hint, not the source of truth. The actual listening port comes from the startup command above. If they differ, trust the command.

Find: Build pattern

Single-stage vs multi-stage. Base image confirms language (python:3.12-slim, golang:1.22-alpine, etc.).

"This is a [language] app, [single/multi]-stage build, running [process] on port [N]. Moving to the app code."
2

App code — routes, health, DB config

"Now I'm looking at the app code to find the health endpoint, main routes, and how it connects to the database."

Django: config/settings.py → */urls.py → */views.py
Python: app.py or main.py
Go: main.go

Sub-step: DB config (Django: config/settings.py  |  others: app entry file)

Find the DATABASES dict (Django) or the DB connection function. Note which env var names it reads: PG*, POSTGRES_*, or DB_*.

"The app reads database config from env vars [list them]. I'll need to check these against the ConfigMap and Secret later."

Sub-step: Routes and health endpoint (Django: */urls.py + */views.py  |  others: app entry file)

Find the health/readiness endpoint path and what it checks (DB query? always 200?). Note the main data route. Don't map every endpoint.

"The health endpoint is [path] and it [checks DB / always returns 200]. The main data route is [path]. This is what the probe must target."

Sub-step: Startup behaviour

Does the app create tables and seed data on startup? Does it run migrations? Will it crash if the DB is unreachable?

"On startup, the app [seeds data / runs migrations via init container / crashes if DB is down]. That tells me what failure looks like if a dependency is misconfigured. Moving to the Deployment manifest."
3

Deployment manifest

"Now I'm checking how Kubernetes actually runs this app — image, config injection, probes, and init containers."

Find: Image + imagePullPolicy

Note the image name and tag. If imagePullPolicy: Never, the image must be pre-loaded on the node.

"The image is [name:tag] with pull policy [value]."

Find: command / args

If present, this overrides the Dockerfile CMD. If absent, the Dockerfile CMD applies.

"[There is / there is no] command override. The container starts with [CMD from Dockerfile / override command]."

Find: envFrom (ConfigMap + Secret references)

Note the exact names. These must exist in the namespace. A typo here causes CreateContainerConfigError.

"Config comes from ConfigMap [name] and Secret [name]. I'll verify those exist and have the right values."

Find: Probes (readiness + liveness)

Note path, port, and timing. The path must match the health endpoint I found in the app code. The port must match the container's listening port.

"Readiness probe hits [path] on port [N], liveness hits [path] on port [N]. That [matches / doesn't match] what the app serves."

Find: Pod template labels

These are what the Service selector must match. Note the exact key-value pairs.

"Pod labels are [key: value]. The Service selector must match this exactly."

Find: Init containers

How many? What does each do? Which ones read from ConfigMap/Secret? The main container won't start until all init containers succeed.

"There are [N] init containers: [what each does]. [They read / don't read] from the same ConfigMap/Secret as the main container. Moving to the Service."
4

Service manifest

"Now I'm checking how traffic reaches the pods."

Find: Selector

Compare character-for-character against the pod template labels from the Deployment. Any difference means empty endpoints.

"Service selector is [key: value]. That [matches / doesn't match] the pod labels I saw in the Deployment."

Find: port → targetPort

port is what Ingress and other services connect to. targetPort must match the container's listening port.

"Service maps port [X] to targetPort [Y]. That targetPort [matches / doesn't match] the container port [N] from the Dockerfile. Moving to the Ingress."
5

Ingress manifest

"This is the last hop before the user-visible URL."

Find: Backend service name + port

The service name must match the Service I just read. The port must match the Service port (not targetPort).

"Ingress routes [path] to service [name] on port [N]. That [matches / doesn't match] the Service I just checked."

Find: ingressClassName, host, path

ingressClassName must match the installed controller (usually nginx). If a host is set, requests need a matching Host header.

"IngressClass is [name], path is [path]. That should be enough to verify the external routing chain. Moving to config if I need to check values."
6

ConfigMap + Secret — check when needed

"I'm checking whether the config values match what the app and the database actually expect."

Find: DB hostname value

The DB host env var must point to the DB Service name (not the Deployment name). Compare against kubectl get svc later.

"DB host is set to [value]. I need to confirm that's the actual DB Service name."

Find: Credentials + DB name

User, password, and database name must match between the app's Secret/ConfigMap and the database's Secret/ConfigMap.

"Credentials and DB name [match / don't match] between the app config and the database config. That's the most common failure domain."

Find: Object names

The ConfigMap and Secret names must match what the Deployment envFrom references. A one-character typo here blocks the container from starting.

"ConfigMap name is [X], Secret name is [Y]. Those [match / don't match] what the Deployment references. I've finished reading the key files."
After orientation — First live checks

Do the objects exist and match what you read?

kubectl get pods -n <ns>                # Running + Ready?
kubectl get svc -n <ns>                 # Service exists, correct ports?
kubectl get ingress -n <ns>             # If ingress exists: ADDRESS populated?
kubectl get endpoints -n <ns>           # If checking routing: endpoints populated?

Only curl if you already have a port-forward running or if the environment exposes the app to localhost (e.g. k3d/kind with port mappings). Do not assume curl localhost/ works by default.

"Now that I know what should exist from reading the files, I'm checking whether the live pods, services, and ingress objects match that expectation."
Scope control — Don't go deeper than this

You are done orienting when you can answer the 5 questions

If you can say what the app is, what starts it, what port it listens on, what paths matter, and which manifests wire it — stop reading and start working. Do not try to understand the whole codebase.

  • Don't read models/serializers in detail
  • Don't map every endpoint
  • Don't study framework conventions
  • Don't read test files
  • Don't read business logic
  • Don't inspect CI/CD config
  • Don't read every manifest field
  • Don't panic if the framework is unfamiliar
"I have enough context to understand how this app is built, configured, and deployed. I'm going to move on to the task now."
