Phase 1 — Scan (30 seconds)

Get the repo map

Run these commands. Don't open any files yet.

ls
tree -L 2          # or: find . -maxdepth 2 -type f | sort
cat README.md      # skim only — what is this app, how to run it
"I'm mapping the repo first — where the app code is, where the build config is, and where the Kubernetes manifests live. This tells me the deploy model before I read any details."
Phase 2 — Read key files (3-4 minutes)

Open files in this order. Extract tagged facts from each.

Each file feeds multiple buckets. Don't jump between files — read one, extract everything, move on.

Project structure (from Phase 1 scan)
  • Shape Framework pattern — flat file (Flask/Go) vs project+app packages (Django) vs module tree (Node)
  • Shape Where are routes defined? Where is DB config? (same file, or separate config/settings?)
  • Start Is there a manage.py, go.mod, requirements.txt, package.json? — confirms language and dependency model
"The project structure tells me this is a [framework] app. Routes are in [file], DB config is in [file]. This tells me where the contracts between the app and the platform config live, and which files I need to read next."
Dockerfile
  • Shape Base image, language, single-stage vs multi-stage build
  • Start CMD / ENTRYPOINT — what process runs (gunicorn? compiled binary? node?)
  • Start EXPOSE — what port the container expects
  • Start If CMD references a WSGI/ASGI module path (e.g. config.wsgi:application), note which project package it points to
"The Dockerfile tells me this is a [language] app running [process] on port [N]. The entry point is [CMD]. This port is the contract that the Service targetPort and probe port must match."
App code — find routes, DB config, and health endpoints

Flask/Go: single file — routes, DB connection, and health check are all in app.py / main.go.
Django: split across files — DB config in config/settings.py, routes in <app>/urls.py, endpoints in <app>/views.py, data model in <app>/models.py.

  • Shape Routes/endpoints — what the app does, what paths it serves
  • Signals Health/readiness endpoints — what path, what they check (DB? always 200?)
  • Supply Where DB config comes from — env vars read directly (Flask/Go) or via settings file (Django)
  • Supply Which env var names? (PG*, POSTGRES_*, DB_* — varies by app)
  • Start Startup behaviour — does the app seed data on boot? Run migrations? Crash if DB is unreachable?
"The app has [N] endpoints at [paths]. Health check is [path] and it [checks DB / always returns 200] — this is the path the readiness probe must target. DB config comes from env vars [list] read in [file]. On startup it [seeds/migrates/crashes if DB down], which affects what failure looks like if a dependency is misconfigured."
Deployment manifest
  • Ship Image name/tag, imagePullPolicy, replicas
  • Ship Labels on pod template (used by Service selector)
  • Start command / args — if present, overrides Dockerfile CMD
  • Supply env / envFrom — which ConfigMaps and Secrets inject env vars
  • Supply volumeMounts — any mounted files or PVCs
  • Signals Probes — path, port, timing. Are readiness and liveness the same path or different?
  • Ship initContainers — how many? What does each one do? (wait for dependency? run migrations? load data?) Which ones read from ConfigMap/Secret?
"The Deployment runs image [X] with [N] init containers: [list what each does]. Config comes from [ConfigMap/Secret names] — these are the naming contracts I need to verify exist. Probes target [path:port], which must match what the app actually serves. Migrations/seeding happen [in init container / at app startup / not at all]."
ConfigMap + Secret manifests
  • Supply Actual values: DB host, port, database name, creds
  • Supply Cross-reference: do these match what the app code expects?
"Config points to [DB host] on port [N], database [name]. Credentials are in [Secret name]. I'm cross-referencing these against the Service name and the app's expected env vars — any mismatch here is the most common failure domain."
Service manifest
  • Ship Selector — must match Deployment pod labels
  • Ship Port (what other things connect to) and targetPort (must match container port)
  • Ship Type (ClusterIP / NodePort / LoadBalancer)
"Service selects pods with [labels], maps port [X] to targetPort [Y]. The selector is the label contract with the Deployment, and the targetPort is the port contract with the container. If either drifts, traffic silently fails while pods look healthy."
Ingress manifest
  • Ship IngressClassName, host, path rules
  • Ship Backend service name and port — must match Service
  • Signals If this is wrong, curl from outside fails but pod-level curl works
"Ingress routes [path] to service [name] on port [N]. This is the last hop before the user-visible URL — if the backend name or port doesn't match the Service, external access fails while internal routing still works."
Database Deployment + Service + PVC (if present)
  • Supply DB image, version, credentials (must match app's config)
  • Ship DB Service name (this is what the app uses as PGHOST / DB_HOST)
  • Ship PVC — storage for data persistence
  • Signals DB probes — pg_isready or similar
"Postgres runs as [image:version], the Service name is [X] — that's the hostname the app config must point to. Creds and DB name must match between the app's ConfigMap/Secret and the database's ConfigMap/Secret. Any mismatch here breaks the app at startup or runtime."
Signal commands to run

After reading the files, check the live cluster to see if reality matches what you read.

kubectl get pods -n [namespace]                # Are all pods Running + Ready?
kubectl get endpoints -n [namespace]           # Are endpoints populated for each Service?
kubectl describe pod [app-pod] -n [namespace]  # Events, probe status, env source errors
kubectl logs [app-pod] -n [namespace]          # Startup errors, DB connection failures
curl [host][path]                              # Hit each route from the Ingress — host/port/path come from what you just read
"Files told me what should happen. These commands tell me what is actually happening. Any gap between the two is where the problem lives — and I want to verify the full user-visible path, not just that pods are Running."
Phase 3 — Summarize (30 seconds)

Now narrate what you know, organized by bucket

This is when the mental model matters. Speak through each bucket in order.

Shape

"This is a [framework] API with [N] endpoints for [purpose],
backed by [database], deployed via [raw manifests / Helm / Kustomize] into the [namespace] namespace."

Start

"Containerized with Docker — runs [process] on port [N].
[N] init container(s): [list what each does — wait for DB / run migrations / load seed data].
Migrations/seeding happen [in init container / at app startup / not at all].
If the DB isn't reachable, [init container loops / app crashes / app degrades]."

Supply

"The app needs [N] env vars for [database] — [list them].
These come from ConfigMap [name] and Secret [name].
DB host points to service [name] — this is the naming contract between the ConfigMap and the DB Service.
Creds and DB name [match / don't match] between the app config and the database config — any mismatch here is the most common failure domain."

Ship

"Deployment runs [N] replicas with [readiness / liveness] probes on [path:port].
Service maps port [X] to targetPort [Y].
Ingress routes [path] to the service on port [X] via [nginx / traefik].
Labels and selectors [match / don't match] throughout — this chain of contracts is what I'd check first if traffic isn't reaching the app."

Signals

"If the DB is down, the app [crashes / degrades] — I'd see [CrashLoopBackOff / 503s] and connection errors in logs.
If probes fail, endpoints would be empty.
If the Service selector is wrong, endpoints empty but pods Running.
If Ingress is wrong, direct pod curl works but external curl doesn't.
Each of these failure modes looks different to users — knowing which signals map to which layer is what lets me triage fast."

What not to do

  • Don't try to fill buckets one at a time — you'll re-read files
  • Don't read the whole codebase — find the key files (routes, config, models) and stop
  • Don't explain business logic in depth
  • Don't start fixing before you've read the key files
  • Don't narrate while reading — extract first, narrate at the end

The connection chain to verify

App reads DB host from env var [PGHOST / POSTGRES_HOST / DB_HOST]
  → Deployment envFrom references ConfigMap [name]
    → ConfigMap value = DB Service name [name]
      → DB Service selector = DB pod labels
        → DB pod is Running + Ready

App listens on port [N]
  → Deployment containerPort = [N]
    → Service targetPort = [N], port = [M]
      → Ingress backend port = Service port [M]
        → curl localhost/ works
The mental model organizes your summary. The file order organizes your reading. Don't mix them up.
