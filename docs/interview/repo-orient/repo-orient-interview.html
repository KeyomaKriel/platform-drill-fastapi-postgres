Interview Quick Reference

Repo Orientation

Recognize the app fast. Open the right files. Extract the contracts. Say what you’re checking as you go.

You do not need deep framework knowledge. You need fast pattern recognition and a clean repo-to-runtime story.
10 seconds — Spot the app type

What kind of repo is this?

Django

manage.py
config/ or project/
views.py, urls.py
models.py, migrations/
Routes
*/urls.py + */views.py
Config
config/settings.py
Entry
manage.py or gunicorn config.wsgi:application
“This looks like a Django app. manage.py is the signal. I’d expect settings in the project package, routes in urls.py, and handlers in views.py.”

Python (Flask / FastAPI)

app.py or main.py
requirements.txt
fewer framework folders
Routes
often in app.py or main.py
Config
env vars read directly in app code
Entry
gunicorn / uvicorn + app module
“This looks like a simpler Python service. Routes and startup logic should be concentrated in one or two files.”

Go

go.mod
main.go
maybe cmd/, internal/, pkg/
Routes
often in main.go or handler files
Config
env vars usually read in startup code
Entry
compiled binary in Dockerfile CMD
“This is a Go service. go.mod and main.go are the signals. I’m checking main.go for startup, routes, and the listening port.”
30 seconds — Map the repo

Get the shape before opening files

pwd
ls
tree -L 2          # or: find . -maxdepth 2 -type f | sort
cat README.md      # skim only
“I’m mapping the repo first so I know where the app code, container config, and Kubernetes manifests live before I go into details.”
3–4 minutes — Open these files in order

Open one, extract the key facts, move on

1

Dockerfile

  • Start CMD / ENTRYPOINT — what process actually starts.
  • Port EXPOSE — useful clue, but not the source of truth by itself.
  • Build base image, language, multi-stage vs single-stage.
The actual listening port comes from what the app binds to in the startup command or app code. Probes and targetPort must match that real listening port, not just whatever EXPOSE suggests.
“I’m checking what actually starts in the container and which port it really listens on, because that has to line up with probes and Service targetPort.”
2

App code — routes, health, config

Django: config/settings.py → */urls.py → */views.py  |  Python: app.py / main.py  |  Go: main.go

  • Routes main user-visible route.
  • Probe health/readiness route and what it checks.
  • Failing Path the exact failing path if the scenario gives one.
  • Config obvious DB env var names: PG*, POSTGRES_*, DB_*, etc.
  • Startup whether startup runs migrations, seeds data, or fails hard when the DB is unreachable.
You are not trying to understand the whole app. You are trying to learn what paths exist, what the probe should target, and what inputs the app expects.
“I’m checking which paths the app really serves and whether health endpoints exist, because probe-path mismatches are a common failure.”
3

Deployment manifest

  • Image image name/tag and imagePullPolicy.
  • Override command / args — these override the Dockerfile.
  • Config env / envFrom — which ConfigMaps and Secrets are referenced.
  • Probes readiness/liveness path, port, and timing.
  • Port containerPort — useful check, but the app still has to bind there.
  • Labels pod template labels — the Service selector must match these.
  • Init init containers and what each one does.
This is where most breakable contracts live: startup override, config injection, labels, probes, and init behavior.
“Now I’m checking how Kubernetes runs the app: image, startup override, config injection, probes, labels, and init containers.”
4

Service manifest

  • Selector must match Deployment pod labels exactly.
  • Ports port is what callers hit; targetPort must match the actual app listening port.
  • Type ClusterIP, NodePort, or LoadBalancer.
Healthy pods with an incorrect selector still give you empty endpoints and broken traffic.
“This tells me how traffic reaches the pod. The selector must match pod labels, and targetPort must match the app’s listening port.”
5

Ingress manifest

  • Routing ingressClassName, host, and path rules.
  • Backend backend Service name and port — must match the Service exactly.
This is the outside-facing contract. If external access fails while internal routing works, this layer moves up the list.
“This is the user-visible entry path. If the app is unreachable externally, this is one of the first contracts I’d verify.”
6

ConfigMap / Secret — inspect when needed

  • Names ConfigMap/Secret names must match what the Deployment references.
  • Values DB host should match the DB Service name; DB name/user/password should line up on both sides.
Config mismatches are one of the most common causes of startup and readiness failures.
“I’m checking whether the config names and values actually match what the app and dependent service expect.”
Do not waste time on this

Narrow the scope aggressively

  • Do not get pulled into business logic.
  • Do not read models or serializers unless the bug clearly points there.
  • Do not try to understand every framework convention.
  • Do not inspect every route in the app.
  • Do not inspect every YAML field.
  • Stop once you know startup, listening port, main route, health route, probes, Service, Ingress, and config references.
“I’m not trying to understand the whole application. I’m narrowing to the startup path, traffic path, and config contracts that would explain the failure.”
After repo orientation — first live checks

Now verify the cluster matches what you just read

kubectl get pods -n <ns>
kubectl get svc -n <ns>
kubectl get ingress -n <ns>       # if ingress exists
kubectl get endpoints -n <ns>     # if checking service routing
“Now that I know what the repo says should exist, I’m checking whether the live pods, services, and ingress objects match that expectation.”
Do not default yet to: kubectl describe pod, kubectl logs, curl localhost, or hitting multiple endpoints. Use those only after these quick checks tell you which layer looks wrong. Also, curl localhost only makes sense if a port-forward or local routing already maps localhost to the app.
Small final recap

Use the buckets only to summarize at the end

Shape

“This is a [framework] API for [purpose], backed by [DB].”

Start

“It runs [process] on [port]; init behavior is [summary].”

Supply

“Config comes from [CM/Secret]; DB host should resolve to [service].”

Ship

“Traffic path is Ingress → Service → Pod.”

Signals

“The main things I’d expect to fail are probes, selector/ports, or config refs.”
