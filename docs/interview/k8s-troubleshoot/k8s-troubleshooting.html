K8s Troubleshooting

Frame Orient Triage Truth Source Cautions Scope Symptoms Domains Views Config Source Entry Path Verify Say Commands

Execution Model

Rule: Symptom first, root cause second.
Loop: classify the symptom → inspect the nearest layer/object → route by evidence → make the smallest justified fix → verify end to end.
Guard: CrashLoopBackOff ≠ cause Running ≠ healthy Ready ≠ ingress works Service exists ≠ endpoints exist Ingress exists ≠ external routing works

Core Frame

1. Start

Was the pod created, scheduled, and able to start its container?
  • No pod
  • Pod Pending
  • ContainerCreating
  • ErrImagePull / ImagePullBackOff
  • CreateContainerConfigError
  • Init container failure
  • Wrong version running

2. Stay Up

Did the app keep running and become Ready?
  • CrashLoopBackOff
  • Running but 0/1 Ready
  • Restarts increasing
  • OOMKilled / exit 137
  • Multi-container log confusion

3. Receive Traffic

Can traffic reach the app through the K8s routing path?
  • Service path fails
  • Endpoints empty
  • External route fails
  • Works inside container only

4. Reach Dep

Can the app reach what it depends on?
  • Feature fails on DB/API
  • DNS / hostname failure
  • Forbidden / Unauthorized
  • Traffic silently blocked

30-Second Orientation

Before deep debugging

Find the cluster/context, namespace, entry path, and config source before guessing.
kubectl config current-context
kubectl config get-contexts
kubectl config use-context <context-name>
kubectl config view --minify
kubectl get ns
kubectl config set-context --current --namespace=<ns>

kubectl get ingress -A
kubectl get svc -A
kubectl get deploy -A

Default Triage Loop

Use this when the symptom is unclear or you just sat down.

1 kubectl get pods -n <ns>
2 kubectl get deploy -n <ns>
3 Pod unhealthy? → describe pod + logs + --previous
4 Deployment not progressing? → describe deploy + rollout status
5 Pod Running/Ready? → get svc + get endpoints
6 Service works internally? → check ingress / external route
7 App still fails? → dependency path from inside pod
8 Make one fix
9 Verify end to end

Nearest Truth Source

Pod not runningdescribe pod + logs
Deployment not progressingdescribe deploy + rollout status
Pod Running/Ready but app unreachableService / endpoints
Service works but external path failsIngress
App responds but feature failsDependency path from inside pod

Do Not Over-Infer

CrashLoopBackOff does not tell you the cause
Running does not mean healthy
Ready does not prove ingress works
Existing Service does not mean it has usable endpoints
Ingress object existing does not mean external routing works
Wrong context or namespace can make a healthy app look missing

1. Startup / Crash

Stay Up
Logs show an app-level crash: unhandled exception, missing module, bad syntax, stack trace, or exit code 1. The container process itself is failing. If logs point to a wrong config value or unreachable dependency, route to Config / Secret / Env or App-Level instead.
"The logs show the app is crashing on startup with [error]. This is the app itself failing, not a config or dependency issue."

Commands

kubectl describe pod <pod> -n <ns>                    # State, Last State, exit codes, Events
kubectl logs <pod> -n <ns>
kubectl logs <pod> -n <ns> --previous                 # last crashed attempt
kubectl logs <pod> -c <container> -n <ns>             # init containers or sidecars

Exit code reference

  • 0 — Clean exit (unexpected for long-running). Check restartPolicy, command/args.
  • 1 — Application error. "Exit code 1 — the app itself is crashing." Read the logs.
  • 127 — Command not found. Binary missing or wrong command override in deployment.
  • 137 — OOMKilled (128+9). Route to Resource / Scheduling.
  • 143 — SIGTERM. Usually liveness kill → route to Probe Failure.

Init container failures

If the pod shows Init:0/1 or Init:CrashLoopBackOff: "The init container hasn't completed. The main container won't start until it succeeds."

kubectl describe pod <pod> -n <ns>                    # find init container name
kubectl logs <pod> -c <init-container> -n <ns>
kubectl get svc -n <ns>                                # what init is waiting on

Likely fixes

  • Bad image or broken binary → kubectl rollout undo deploy/<deploy> -n <ns>
  • Bad command/args override → kubectl get deploy -o yaml | grep -A5 "command\|args" — remove or correct the override with kubectl apply -f manifests/
  • App crash from bad config → fix the ConfigMap/Secret (see Config / Secret / Env), then kubectl rollout restart

Verify

kubectl get pods -n <ns>              # Running, restarts stop climbing
kubectl logs <pod> -n <ns>            # clean startup, no errors
"Restarts have stopped, pod is staying Running, logs are clean."

2. Image Pull / Container Creation

Start
Pod shows ImagePullBackOff, ErrImagePull, ErrImageNeverPull, CreateContainerConfigError, or CreateContainerError.
"The pod is stuck at [status]. Let me check the Events section to see exactly what failed."

Commands

kubectl describe pod <pod> -n <ns>
kubectl get pod <pod> -n <ns> -o jsonpath='{.spec.containers[0].image}'
kubectl rollout history deploy/<deploy> -n <ns>       # find last known-good image

What the output implies

  • Image pull failures — Events show Failed to pull image. Compare against known-good image. Check tag, registry, imagePullPolicy.
  • CreateContainerConfigError — Pod references a Secret or ConfigMap that doesn't exist. Events name the missing object.
  • CreateContainerError — Entrypoint or command doesn't exist in image. Check command/args in pod spec.
  • ErrImageNeverPull — imagePullPolicy: Never but image not on node. Common in kind/k3d.

Likely fixes

# Fix image name or tag
kubectl set image deployment/<deploy> <container>=<correct-image>:<tag> -n <ns>

# Rollback entirely
kubectl rollout undo deploy/<deploy> -n <ns>

# Missing ConfigMap/Secret causing CreateContainerConfigError
kubectl create configmap <cm> --from-literal=KEY=value -n <ns>
kubectl create secret generic <secret> --from-literal=KEY=value -n <ns>

Verify

kubectl get pods -n <ns> -w             # pod moves past error, reaches Running
"Pod is past the error state and running."

3. Probe Failure

Stay Up
Pod is Running but not Ready (0/1), or Running with RESTARTS climbing. Readiness failure removes the pod from Service endpoints. Liveness failure kills and restarts the container.
"The pod is Running but [not Ready / restarts are climbing]. Let me check which probe is failing and what it's targeting."

Commands

kubectl describe pod <pod> -n <ns>                    # probe spec + Conditions
kubectl get pod <pod> -n <ns> -o jsonpath='{.spec.containers[0].readinessProbe}'
kubectl get pod <pod> -n <ns> -o jsonpath='{.spec.containers[0].livenessProbe}'

Test what the app actually responds to

kubectl port-forward pod/<pod> 8080:<container-port> -n <ns>
curl -i localhost:8080/health
curl -i localhost:8080/healthz
curl -i localhost:8080/readyz

What the output implies

  • Wrong probe path — path returns 404, different path returns 200. "Probe targets [path] but the app responds on [other path]."
  • Wrong probe port — connection refused on probe port. "Probe targets port [X] but app listens on [Y]."
  • initialDelaySeconds too short — fails briefly then passes. Increase delay.
  • App genuinely unhealthy — probe is correct, app has a real problem. Check logs → App-Level.

Likely fixes

kubectl edit deploy <deploy> -n <ns>
# Fix readinessProbe.httpGet.path, .port, .initialDelaySeconds
# Fix livenessProbe.httpGet.path, .port, .timeoutSeconds, .failureThreshold

Verify

kubectl get pods -n <ns>                  # 1/1 Ready, or restarts stop
kubectl get endpoints <svc> -n <ns>       # endpoints populate
"Pod is 1/1 Ready, endpoints are populated."

4. Config / Secret / Env

Cross-cutting
Events show a missing ConfigMap or Secret, logs reveal a wrong or missing value, or CreateContainerConfigError points to a missing config reference. Covers: missing objects, wrong reference names, wrong keys, wrong values.
"This is a configuration problem. I need to check what the pod references versus what actually exists, and compare the values."

Commands

kubectl describe pod <pod> -n <ns>
kubectl get configmap -n <ns>
kubectl get secret -n <ns>
kubectl get deployment <deploy> -n <ns> -o yaml | grep -A2 -E 'configMapRef|secretRef'

What the output implies

  • Events: configmap "X" not found or secret "X" not found. "Events name the exact missing resource." Compare character-for-character.
  • envFrom references: Compare character-for-character against what exists. "The deployment references [name] but the actual object is [other name]."

Check values inside existing objects

kubectl get configmap <cm> -n <ns> -o yaml
kubectl get secret <secret> -n <ns> -o jsonpath='{.data.<key>}' | base64 -d
kubectl exec <pod> -n <ns> -- env | sort

Likely fixes

  • Missing object: kubectl create configmap <cm> --from-literal=KEY=value -n <ns>
  • Wrong reference name: kubectl edit deploy <deploy> -n <ns> — fix configMapRef.name or secretRef.name
  • Wrong value: kubectl edit configmap <cm> -n <ns>
  • After any config change: kubectl rollout restart deploy/<deploy> -n <ns>

Verify

kubectl describe pod <pod> -n <ns>               # no Warning events
kubectl exec <pod> -n <ns> -- env | grep <KEY>   # correct values injected
kubectl logs <pod> -n <ns>                        # clean startup
"No warning events, correct values injected, clean startup."

5. Service Routing / Port / Endpoint

Receive Traffic
Pods are Running and Ready but unreachable through the Service. The reachability path found empty endpoints or a port mismatch.
"Pods are healthy but I can't reach them through the Service. Let me check selectors, endpoints, and ports."

Commands

kubectl get endpoints <svc> -n <ns>
kubectl describe svc <svc> -n <ns>
kubectl get pods -n <ns> --show-labels
kubectl port-forward svc/<svc> 8080:<svc-port> -n <ns>

What the output implies

  • Endpoints empty (<none>): "Endpoints are empty — the Service selector matches zero Ready pods." Compare selector against pod labels character-for-character.
  • Wrong targetPort: Must match the container's listening port. kubectl get pod -o jsonpath='{.spec.containers[0].ports[0].containerPort}'
  • Pods not Ready: Even if selector matches, only 1/1 Ready pods appear in endpoints. Fix readiness first → Probe Failure.

Likely fixes

# Selector mismatch
kubectl patch svc <svc> -n <ns> -p '{"spec":{"selector":{"app":"<correct-label>"}}}'

# Wrong targetPort
kubectl patch svc <svc> -n <ns> -p '{"spec":{"ports":[{"port":<svc-port>,"targetPort":<correct-port>}]}}'

Verify

kubectl get endpoints <svc> -n <ns>               # pod IPs populated
kubectl port-forward svc/<svc> 8080:<svc-port> -n <ns>
curl -i localhost:8080/                            # valid response
curl -s localhost/                                 # end-to-end through Ingress
"Endpoints are populated, port-forward works, and the external curl returns a valid response."

6. DNS / Service Discovery / Namespace

Reach Dep
Resources appear missing, DNS resolution fails, or logs show Name or service not known.
"I need to check whether I'm looking in the right place, and whether DNS resolution is working inside the cluster."

Namespace confusion

kubectl get all -A
kubectl get ns
kubectl config view --minify | grep namespace
  • Wrong default namespace → kubectl config set-context --current --namespace=<correct-ns>

7. Resource / Scheduling / Storage

Start
Pod is Pending, exit code is 137 (OOMKilled), or PVC is stuck in Pending.
"The pod is [Pending / OOMKilled / has a storage issue]. Let me find the specific constraint that's blocking it."

Pending pods

kubectl describe pod <pod> -n <ns>                    # Events: scheduling reason
kubectl get nodes
kubectl describe node <node>
kubectl top nodes
  • Insufficient cpu/memory → lower requests in deploy spec
  • no nodes available → taint/affinity/selector mismatch
  • unbound immediate PersistentVolumeClaim → see Storage below

OOMKilled (exit 137)

kubectl describe pod <pod> -n <ns>          # Last State shows OOMKilled
kubectl get pod <pod> -n <ns> -o jsonpath='{.spec.containers[0].resources.limits.memory}'

Fix: kubectl edit deploy <deploy> -n <ns> — increase resources.limits.memory.

Storage (PVC issues)

kubectl get pvc -n <ns>
kubectl describe pvc <pvc> -n <ns>
kubectl get storageclass
kubectl get pv

  • PVC fields are mostly immutable — delete and recreate if spec is wrong

8. Ingress / External Routing

Receive Traffic
Service works via port-forward but the external URL fails. If Service/endpoints are broken, go to Service Routing first.
"I can reach the app through port-forward, so the Service and pods are fine. The problem is in the Ingress layer."

Commands

kubectl get ingress -n <ns>
kubectl describe ingress <ing> -n <ns>
kubectl get ingressclass
kubectl get pods -n ingress-nginx

What the output implies

  • ADDRESS blank: Ingress controller hasn't admitted this resource. Check ingressClassName matches installed controller.
  • Backend port mismatch: Ingress backend port must match Service port, not targetPort. "The ingress backend points to port [X] but the service is on port [Y]."
  • Host/path: If Host: is set, requests need matching Host header. pathType: Exact with /api won't match /.
  • Controller health: kubectl get pods -n ingress-nginx must be Running/Ready.

Likely fixes

# Wrong backend port
kubectl patch ingress <ing> -n <ns> --type=json \
  -p '[{"op":"replace","path":"/spec/rules/0/http/paths/0/backend/service/port/number","value":<correct-port>}]'

# Wrong IngressClass
kubectl patch ingress <ing> -n <ns> -p '{"spec":{"ingressClassName":"nginx"}}'

# Or re-apply from manifest
kubectl apply -f manifests/ingress.yaml

Verify

kubectl get ingress -n <ns>              # ADDRESS populated
kubectl describe ingress <ing> -n <ns>   # Backends show correct service
curl -s localhost/                        # end-to-end

9. NetworkPolicy / Traffic Restriction

Reach Dep
Everything looks correct — pods Running, Ready, endpoints populated — but traffic silently fails or times out with no error message.
"Everything looks healthy but traffic is failing silently. When all the obvious things check out, NetworkPolicy is the first thing I check."

Commands

kubectl get networkpolicy -n <ns>
kubectl describe networkpolicy -n <ns>
kubectl get pods -n <ns> --show-labels

Common broken patterns

  • Allow rule podSelector doesn't match any running pods (label typo)
  • Allow rule namespaceSelector wrong — for ingress-nginx: kubernetes.io/metadata.name: ingress-nginx
  • Missing port specification in allow rule
  • No DNS egress rule — "pods can't resolve hostnames at all"
  • Egress deny with no rule allowing app-to-database traffic

Quick isolation test (interview/sandbox only)

kubectl get networkpolicy -n <ns> -o name
kubectl delete networkpolicy <policy-name> -n <ns>
curl localhost/                                     # test after each deletion

If traffic works after deleting a specific policy, that was the blocker. Re-apply a corrected version.

Likely fixes

  • Wrong podSelector → kubectl edit networkpolicy <policy> -n <ns>
  • Missing DNS egress rule → add egress allow for kube-system on UDP/TCP 53
  • Missing app-to-database rule → add egress allow with correct podSelector and port

Verify

kubectl get networkpolicy -n <ns>
curl -s localhost/                        # traffic flows end-to-end

10. RBAC / Service Account / Permission

Reach Dep
Forbidden or Unauthorized errors. A service account can't perform an action. This bypasses the main pod-state flow.
"I see a Forbidden error. I need to check the ServiceAccount, Role, and RoleBinding to find the broken link in the chain."

Commands

kubectl auth can-i --as=system:serviceaccount:<ns>:<sa> <verb> <resource> -n <ns>
kubectl get sa,role,rolebinding -n <ns>
kubectl get rolebinding <binding> -n <ns> -o yaml
kubectl get role <role> -n <ns> -o yaml

Walk the chain — find the broken link

  • RoleBinding subjects: name must exactly match SA name. namespace must match where SA lives.
  • RoleBinding roleRef: Must match an existing Role. roleRef is immutable — delete and recreate if wrong.
  • Role rules — all three must be correct:
    • apiGroups: [""] for core (pods, services, configmaps), ["apps"] for deployments
    • resources: must be plural (["pods"] not ["pod"])
    • verbs: ["get","list","watch"] not ["read"]

Likely fixes

# Subject name wrong — edit binding
kubectl edit rolebinding <binding> -n <ns>

# RoleRef wrong (immutable) — delete and recreate
kubectl delete rolebinding <binding> -n <ns>
kubectl create rolebinding <binding> --role=<role> --serviceaccount=<ns>:<sa> -n <ns>

# Role missing permissions
kubectl edit role <role> -n <ns>

Verify

kubectl auth can-i --as=system:serviceaccount:<ns>:<sa> <verb> <resource> -n <ns>
# Expected: yes

11. Application-Level Dependency / Runtime

Reach Dep
Pods are Running and Ready, endpoints populated, but the app returns errors or doesn't respond. Kubernetes thinks everything is fine — this is an app-level issue.
"Everything looks healthy from a Kubernetes perspective. This is an application-level issue. Logs should tell me what's going on."

Commands

kubectl logs <pod> -n <ns>
kubectl logs <pod> -n <ns> --previous
kubectl exec <pod> -n <ns> -- env | sort
kubectl get configmap <cm> -n <ns> -o yaml
kubectl get secret <secret> -n <ns> -o jsonpath='{.data.<key>}' | base64 -d

What logs typically show

  • connection refused to DB host → wrong hostname or DB not running. "Let me check if the service exists." kubectl get svc -n <ns>
  • password authentication failed → wrong credentials. Compare decoded Secret against authoritative source.
  • database "X" does not exist → wrong DB name in config. Compare pod env against Postgres ConfigMap.
  • Name or service not known → DNS failure. Route to DNS.
  • App returns 404 on expected paths → wrong base path or route config. Check env vars.
  • App bound to 127.0.0.1 → needs to bind to 0.0.0.0. Check Dockerfile CMD or env vars for listen address.

Diagnostic pattern

kubectl exec <pod> -- env | sort to see runtime values. Compare each value against the authoritative source: kubectl get svc for hostnames, ConfigMap for DB name/user, decoded Secret for passwords.

Likely fixes

  • Wrong ConfigMap value: kubectl edit configmap <cm> -n <ns>, then kubectl rollout restart
  • Wrong Secret value: kubectl edit secret <secret> -n <ns> (base64-encoded), then kubectl rollout restart
  • Schema not initialized: restart may trigger migrations if the app runs them on startup

Verify

kubectl logs <pod> -n <ns>                   # no connection or auth errors
kubectl exec <pod> -n <ns> -- env | sort     # env vars correct
curl -s localhost/                            # app responds through full path

Entry Path View

How to determine the app entry path

Ingress? If yes, use host + path. If no, inspect Service type.
# 1. Is there an Ingress?
kubectl get ingress -n <ns>
kubectl describe ingress <ingress> -n <ns>

# 2. If not, inspect the Service
kubectl get svc -n <ns>
kubectl describe svc <service> -n <ns>
  • Ingress: use host from Ingress rule and path from Ingress path
  • LoadBalancer Service: use external IP/DNS + service port + app endpoint path
  • NodePort Service: use node IP + nodePort + app endpoint path
  • ClusterIP Service: internal only; use service DNS name or port-forward
  • App endpoint path: get it from probe path, repo docs, curl scripts, or app routes

Example curl patterns

Use the object spec to build the exact curl command.
# Ingress with host rule
curl -H "Host: <host>" http://<ingress-ip><path>

# Local ingress
curl -H "Host: <host>" http://localhost<path>

# LoadBalancer Service
curl http://<external-ip-or-dns>:<port><path>

# NodePort Service
curl http://<node-ip>:<nodePort><path>

# Internal-only ClusterIP Service
kubectl port-forward svc/<service> 8080:<service-port> -n <ns>
curl http://localhost:8080/<path>

Verification Commands

After any fix, verify in this order:

Pod state — kubectl get pods -n <ns>
Readiness — confirm 1/1 Ready, RESTARTS stable
Endpoints — kubectl get endpoints <service> -n <ns>
Service path — kubectl port-forward svc/<service> 8080:<port> -n <ns>, then curl localhost:8080/health
Ingress path — curl localhost/ (or curl -H "Host: <host>" http://<ingress-ip>/)
App end to end — curl localhost/health and curl localhost/items
Do not stop at "Pods are Running". Services depend on backend endpoints, and ingress only proves the external edge if the backend chain is sound.

What to Say in the Interview

"I'm going to start with the symptom, not jump to a root cause."
"First I want the nearest truth source."
"If the Pod is broken, I'll inspect Pod state, describe output, and logs."
"If the Pod is Running and Ready, I'll move outward from Pod to Service to Ingress."
"I want to make one justified change, then verify end to end."
"I want to separate app-level failure from Kubernetes routing failure, so I'll test the pod directly first, then the Service, then ingress if needed."
"I want to identify the entry object first. If there is an Ingress, I'll use its host and path rules. If there is no Ingress, I'll inspect the Service type to see whether this is external LoadBalancer/NodePort access or internal ClusterIP routing."

That matches the official debugging flow and shows controlled reasoning rather than guesswork.
